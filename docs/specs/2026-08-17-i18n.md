# Internationalization

**Status: Built** (corrected 2026-09-23; it said "proposed"). `LanguagePicker`
(`app/src/components/LanguagePicker.tsx`) is in the app header and on the landing page. The
dictionaries for 35 locales and their spoken-string templates are in `app/src/i18n/` and
`app/src/i18n/speech/`. The first build was `4c90f90` (2026-08-17). The 2026-09-01 addendum
(one URL per language, prerendered) is built too: `pathForLocale` in `app/src/lib/i18n.ts`.
This correction does not check phase 4, the RTL audit, rule by rule.

A globe control in the header opens a searchable language picker. The
app supports the languages Apple ships as system languages. This document is the plan a
subagent can implement from.

## The control

A globe-outline icon button in the header, next to the Network menu (`app/src/App.tsx`,
header block ~line 289). Icon-only, like the view icons — and like them it carries its word:
`aria-label` names the control and the current language ("Language: English"), a tooltip
shows the same (`TipUnder` pattern, `App.tsx:263`).

The picker is **not** the house `Menu` — `Menu.tsx:13` documents that typeahead is the one
thing it does not do, and forty languages need search. Build `LanguagePicker`:

- A popover (same `menu-list` styling) with a text input at the top and a listbox under it.
  A text input is fine; the ban in ui-layout-standards is on `<select>`, checkboxes, radios.
- Filter as you type, matching the endonym ("Español"), the English exonym ("Spanish"), and
  the BCP-47 code ("es"). Case- and accent-insensitive.
- Each row: endonym primary, exonym as the dim hint (reuse `menu-item` / `menu-lead`).
- Keyboard: arrows move, Enter picks, Escape closes and returns focus, exactly as `Menu`
  behaves. The input keeps focus while arrows move the active row (`aria-activedescendant`).

## The languages

Apple's iOS/macOS system-language list, folded by script where a regional variant adds
nothing this app says differently. The fold rule is part of the spec so "all languages Apple
supports" stays honest:

en, zh-Hans, zh-Hant, ja, ko, fr, de, es, es-419, it, pt-BR, pt-PT, nl, sv, da, nb, fi, ru,
pl, tr, ar, he, th, vi, id, ms, hi, el, cs, sk, hu, ro, uk, hr, ca

Folds: en-GB/AU/IN/CA → en · fr-CA → fr · es-MX/US → es-419 · zh-HK → zh-Hant. If Apple's
list grows, the registry grows; the registry is one array.

## Architecture

`app/src/lib/i18n.ts`:

- `LOCALES`: `{ code, endonym, exonym, rtl? }[]` — the registry above.
- Selection in `localStorage` (`prove.locale`). First load resolves from
  `navigator.languages` against the registry, base-language match, fallback `en`.
- `t(key, vars?)`: dictionary lookup with `{var}` interpolation, falling back to English.
  Missing key = English string, never the key.
- `useLocale()` via `useSyncExternalStore`; `App` subscribes at the root so a change
  re-renders the tree.
- On change: set `document.documentElement.lang` and `dir` (rtl for ar, he).

Dictionaries: `app/src/i18n/en.ts` is the source of truth and loads statically. Every other
locale is a module loaded with a dynamic `import()` so Vite splits them out of the main
bundle. A locale file exports `Partial<typeof en>` — untranslated keys fall through.

## Scope, in phases

The string surface is large and much of it is load-bearing accessibility prose. Do not
translate it all in one pass.

1. **Chrome** (~50 keys): header (tabs via `VIEW_LABEL`/`VIEW_TIP` in `ViewIcon.tsx`,
   Network, Connect, endpoints button), board stats labels, scope/sort/filter controls,
   empty states, footer, `RpcSettings` copy. Ship all locales for these keys.
2. **The three views' bodies**: `Compose.tsx`, `Portfolio.tsx`, `BatchTray.tsx`,
   `IntentRow.tsx`, `TokenPicker.tsx`, `Tour.tsx`.
3. **Spoken strings**: `app/src/lib/speech.ts` builds English sentences by concatenation
   (`spokenAmount`, `spokenDuration`, `spokenRate`). Concatenation does not translate —
   these become per-locale template functions. Until phase 3, screen-reader sentences stay
   English; say so in the picker row for partially translated locales if we care.
4. **RTL audit**: setting `dir=rtl` is one line; the layout uses physical utilities
   (`ml-auto`, `text-right`, `pl-3`). Migrate to logical ones (`ms-auto`, `text-end`) or
   scope exceptions. Arabic and Hebrew are not "supported" until this pass is done.

Numbers and dates: `App.tsx:90` hardcodes `toLocaleDateString('en-US')`; route every date and
`Intl.NumberFormat` use through the active locale. `fmt`/`fmtCompact` in the SDK stay
locale-neutral (they feed `.num` columns and URLs); only the presentation layer localizes.

## What does not change

- Route tokens (`board`, `sign`, `mine`, `cleanup` in `routes.ts`) are protocol, not copy.
- Token symbols, addresses, hashes, units.
- The `num` class and tabular figures.

## Acceptance

- Picker lists every registry language, searchable, keyboard-complete, screen-reader-named.
- Switching languages re-renders in place, persists, and survives reload; `lang`/`dir` are
  set.
- English never appears as a raw key; missing translations fall back silently.
- Bundle: non-English dictionaries load on demand, not in the main chunk.
- 375px: the picker fits the viewport, the header still wraps cleanly (see
  `2026-08-17-responsive-visuals.md`).

## Addendum, 2026-09-01: a language a search engine can find

Everything above chooses a language at run time, from `localStorage` and then
`navigator.languages`. That serves a person and serves no crawler at all. Googlebot fetches
with `Accept-Language: en` and reports one English tag in `navigator.languages`, so the
picker answers English every time it is asked. Thirty-four translations that only exist
after a click are, to a search engine, not on the internet.

Three things fix it, and all three are needed together:

1. **A URL per language.** `/` is English and `/<code>/` is everything else, lower case —
   `pathForLocale` in `lib/i18n.ts`. A search engine indexes URLs, so a language without one
   has nowhere to be indexed. The registry's own casing (`zh-Hans`, `pt-BR`) stays in the
   `hreflang` attribute, which is a BCP-47 tag; the path is bytes and is folded down.
2. **The words in the HTML that URL serves.** `scripts/prerender.ts` runs after `vite build`
   and writes one static file per locale, rendered through Vite so `lib/i18n`'s module state
   is the same instance the components read. The markup is a seed, not a hydration target:
   `main.tsx` still calls `createRoot`, which discards it. The point is that the sentences
   are in the first response.
3. **`hreflang`, complete and mutual.** Each of the thirty-five pages lists all thirty-five
   plus `x-default`. An incomplete or one-sided cluster is one Google drops, leaving
   thirty-five pages that look like thin duplicates of each other. `sitemap.xml` repeats the
   cluster, because that is the copy Search Console reads first.

The URL now leads the bootstrap — path, then stored choice, then browser — and a language
read off the path is not stored, so a shared `/ja/` link does not make somebody's browser
Japanese for good. `keepLocale()` is called on the one crossing into the app, which has no
locale in its own URL.

`src/lib/seo.ts` generates the head, the alternates and the sitemap; `seo.test.ts` holds
`index.html` to `head('en')` character for character, so the file Vite serves in development
cannot drift from the file the crawler gets.

**Still open**: `/app` is one URL in whatever language the reader carries into it. It is
behind a wallet and has nothing to index, so it points `canonical` at `/` and stops there.
The picker (#60) should navigate to `pathForLocale(code)` rather than only set the language,
so a reader can link to what they are reading.
